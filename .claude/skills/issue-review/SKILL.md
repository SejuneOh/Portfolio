# Issue Review

루프(`issue-loop`)가 만든 PR을 검사하는 **검사 전담 절차**.

## 이 스킬의 유일한 산출물은 코멘트다

| 한다 | 하지 않는다 |
|---|---|
| PR diff를 읽는다 | **코드를 수정한다** |
| 코드를 실행·검증한다 | **커밋·푸시한다** |
| 판정 코멘트를 남긴다 | **병합한다** |
| 라벨을 조정한다 | **브랜치를 만든다** |

수정이 필요하다고 판단되면 **무엇을 고쳐야 하는지 코멘트로 적는다.**
직접 고치지 않는다 — 고치는 순간 검사자가 아니라 작성자가 된다.

## 왜 세션을 분리하는가

코드를 작성한 세션이 같은 코드를 검사하면 **자기 결과를 옹호한다.**
반드시 별도 세션에서 실행한다.

```bash
(cd <레포 경로> && claude --bg --name "review-<N>" "/issue-review <PR번호>")
```

이 세션은 작성 과정을 모른다. **PR diff와 저장소 코드만 보고 판단한다.**
그것이 이 절차가 성립하는 조건이다.

## 절차

### 1. 대상 확인

```bash
gh pr view <PR번호> --repo SejuneOh/Portfolio \
  --json number,title,body,headRefName,baseRefName,labels,state
```

- `state`가 `OPEN`이 아니면 종료
- `agent-loop` 라벨이 없으면 종료 — 사람이 만든 PR은 검사 대상이 아니다

### 2. 읽기 전용 작업 공간

```bash
git fetch origin <headRefName>
git worktree add --detach .claude/worktrees/review-<N> origin/<headRefName>
```

`--detach`로 만든다. **브랜치를 만들지 않는다** — 작성자 쪽 브랜치와 경합하지 않기 위해서다.

이 워크트리에서는 읽기와 검증만 한다. 파일을 고치지 않는다.

### 3. 검사

먼저 diff를 본다.

```bash
gh pr diff <PR번호> --repo SejuneOh/Portfolio
```

**"이 변경이 왜 틀렸는지 찾아라"는 자세로 본다.** "괜찮아 보인다"에서 출발하면
검사가 성립하지 않는다. 아래 관점을 각각 적용한다.

| 관점 | 확인할 것 |
|---|---|
| 이슈 부합 | 이슈가 요구한 것을 실제로 했는가. 요구하지 않은 것을 했는가 |
| 정확성 | 경계값, null/undefined, 빈 배열, 에러 경로가 처리되는가 |
| 범위 | 이슈와 무관한 파일이 변경되지 않았는가 |
| 규칙 위반 | `CLAUDE.md`의 금지 사항을 어기지 않았는가 (시크릿, main 조작, 병합) |
| 안전 | `TRIAGE.md`의 "사람 필요" 영역을 건드리지 않았는가 |
| 되돌리기 | 문제가 생겼을 때 이 PR만 되돌리면 복구되는가 |

이어서 기계 검증을 **직접 다시 돌린다.** 작성자의 주장을 믿지 않는다.

```bash
cd .claude/worktrees/review-<N>
npm ci && npm run lint && npm run build
```

### 4. 판정

| 판정 | 조건 |
|---|---|
| **통과** | 위 관점에서 문제 없음 + `lint`·`build` 통과 |
| **반려** | 하나라도 문제 있음. 무엇을 어떻게 고쳐야 하는지 명시 |
| **사람 필요** | 자동 처리 영역을 벗어난 변경이 포함됨 |

애매하면 **반려**한다. 통과시킨 뒤 사람이 발견하는 것보다 낫다.

### 5. 코멘트

```bash
gh pr comment <PR번호> --repo SejuneOh/Portfolio --body "..."
```

형식:

```markdown
## 검사 결과 — 통과 | 반려 | 사람 필요

**검증:** lint ✅ build ✅  (직접 실행함)

### 확인한 것
- 이슈 #NN이 요구한 <무엇>이 <어디>에 구현됨
- 변경 범위가 <파일들>로 제한됨

### 문제 (반려인 경우만)
1. **<파일>:<줄>** — <무엇이 잘못됐는지>
   → <어떻게 고쳐야 하는지>

### 사람이 확인해야 할 지점
- <판단이 필요한 부분>
```

**"LGTM" 한 줄로 끝내지 않는다.** 무엇을 확인했는지 적지 않은 통과는
검사하지 않은 것과 구별되지 않는다.

### 6. 라벨

| 판정 | 조치 |
|---|---|
| 통과 | `review-passed` 라벨 추가. 사람 리뷰 대기 상태가 된다 |
| 반려 | `review-changes` 라벨 추가. 작성 쪽이 다시 들어온다 |
| 사람 필요 | `needs-human` 라벨 추가 + 연결된 이슈에도 동일 |

### 7. 정리

```bash
git worktree remove --force .claude/worktrees/review-<N>
```

**반드시 지운다.** 남기면 다음 검사가 같은 경로에서 실패한다.
지우지 못했으면 코멘트에 적어 다음 실행이 알 수 있게 한다.

## 재작업 상한

작성 ⇄ 검사가 무한 왕복하는 것을 막는다.

```
1회차 반려 → 작성 쪽 수정 → 재검사
2회차 반려 → 작성 쪽 수정 → 재검사
3회차 반려 → 중단.  needs-human + 사람에게 넘긴다
```

**반려 횟수는 PR의 `review-changes` 라벨 부착 횟수로 센다.**
직접 셀 수 없으면 PR 코멘트에서 `## 검사 결과 — 반려` 등장 횟수를 센다.

3회차에 도달하면 통과시키지 않는다. **넘기는 것이 정상 종료 경로다.**

## 절대 하지 않는 것

- `git commit` / `git push` — 어떤 상황에서도
- `gh pr merge` — 어떤 상황에서도
- 파일 수정 — 사소한 오타라도 코멘트로만 지적한다
- 작성 쪽 워크트리(`issue-<N>`) 접근
- 잠긴(locked) 워크트리 접근
