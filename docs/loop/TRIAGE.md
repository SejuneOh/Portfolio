# TRIAGE — 자동 처리 가능 여부 판정 기준

루프가 이슈를 집기 전에 이 문서로 판정한다. **애매하면 사람에게 넘긴다.**
판정은 매 실행마다 빈 컨텍스트에서 이루어지므로, 여기 적힌 것만이 기준이다.

## 판정 순서

아래를 위에서부터 순서대로 적용한다. 먼저 걸리는 규칙이 이긴다.

### 1. 즉시 제외 (건드리지 않음)

다음 중 하나라도 해당하면 **아무 라벨도 달지 않고 조용히 넘어간다.**
코멘트도 남기지 않는다 — 이미 사람이 의도적으로 관리 중인 이슈다.

- `backlog` 라벨이 있다 — 의도적으로 미뤄둔 작업
- `needs-human` 라벨이 이미 있다 — 이전 실행이 이미 판정했다
- `in-progress` 라벨이 있고 아직 유효하다 — 다른 실행이 작업 중 (회수 규칙은 아래 참조)
- 연결된 열린 PR이 이미 있다
- 이슈가 다른 이슈에 의해 블록되어 있다고 본문에 명시돼 있다

### 2. 사람 필요 (`needs-human` 라벨 + 이유 코멘트)

다음 중 하나라도 해당하면 자동 처리하지 않는다.

**보안·자격증명**
- 인증/인가 로직 변경 (`auth.ts`, `middleware.ts`, `app/api/auth/**`)
- 시크릿·API 키·환경변수 값이 필요한 작업 (`.env*`)
- 레이트리밋·봇 방어 정책 변경 (`lib/rateLimit.ts`)

**되돌리기 어려운 변경**
- 외부 서비스 계약 변경 (Notion 스키마, Vercel 설정, Upstash 구성)
- 공개 API 라우트의 요청/응답 형태 변경
- 의존성 메이저 버전 업그레이드

**판단이 필요한 작업**
- 디자인·비주얼 결정이 필요한 것 (색상, 레이아웃, 타이포그래피 선택)
- 요구사항이 모호하거나 완료 조건이 이슈에 적혀 있지 않은 것
- 콘텐츠 자체를 창작해야 하는 것 (이력서 문구, 프로젝트 소개 글)

**범위가 큰 작업**
- 3개 이상의 디렉터리에 걸친 변경이 예상되는 것
- 이슈 본문에 하위 작업 체크박스가 5개 이상인 것
- "전면 개편", "리디자인", "마이그레이션" 성격의 것

### 3. 자동 처리 가능

위 두 관문을 통과하고 **다음을 모두 만족**할 때만 집는다.

- 완료 조건이 이슈에 명시돼 있거나 코드에서 명확히 도출된다
- 변경 범위가 예상 가능하다 (대략 1~2개 모듈)
- `npm run lint && npm run build`로 검증 가능하다
- 되돌리기 쉽다 (파일 수정 위주, 삭제·이동 최소)

전형적인 예:
- 재현 절차가 있는 버그 수정
- 린트·타입 오류 정리
- 문서·README 보강
- 접근성 속성 추가 (`alt`, `aria-*`)
- 하드코딩된 값을 `config/`로 추출
- 기존 패턴을 따르는 소규모 컴포넌트 추가

## `priority` 라벨의 취급

`priority`는 **순서를 바꿀 뿐 관문을 면제하지 않는다.**

| 관문 | `priority`가 붙어도 |
|---|---|
| 1. 즉시 제외 | `backlog`와 함께 붙어 있으면 **`priority`가 이긴다** (사람이 급하다고 판단한 것) |
| | 그 외 제외 조건(진행 중, 열린 PR 등)은 **그대로 적용**된다 |
| 2. 사람 필요 | **그대로 적용된다.** 급하다고 인증 로직을 자동으로 고치지 않는다 |
| 3. 자동 처리 가능 | 통과하면 최우선으로 처리 — 핫픽스 절차(`PRIORITY.md`)를 따른다 |

2번에 걸리면 `needs-human` + 에스컬레이션이다. **프로덕션이 급한 상황일수록
잘못된 자동 수정의 대가가 크다.** 이 경우 코멘트에 "긴급하나 자동 처리 불가"임을
명시해 사람이 바로 알아볼 수 있게 한다.

`priority` 라벨은 **사람만 붙인다.** 루프는 절대 스스로 붙이지 않는다 —
붙일 수 있으면 루프가 스스로 프로덕션 경로를 열 수 있게 된다.

## `in-progress` 락 회수 규칙

에이전트가 중간에 죽으면 `in-progress` 라벨이 남아 이슈가 영구 교착된다.
**루프 시작 시 가장 먼저** 다음을 수행한다.

`in-progress` 라벨이 붙은 이슈 각각에 대해:

| 조건 | 조치 |
|---|---|
| 연결된 열린 PR이 있다 | 유지 — 정상 작업 중 |
| 라벨이 붙은 지 **2시간 미만** | 유지 — 아직 작업 중일 수 있음 |
| 라벨 2시간 경과 + 열린 PR 없음 | **회수** — 라벨 제거 + 회수 코멘트 |

회수 코멘트 예시:

```
이전 자동 처리 시도가 완료되지 않아 `in-progress` 락을 회수했습니다.
(락 설정: <타임스탬프>, 연결된 열린 PR 없음)
```

라벨이 붙은 시각은 이슈 타임라인에서 확인한다.

## 코멘트 작성 규칙

`needs-human`을 달 때는 **왜 못 하는지**를 구체적으로 적는다.
"처리할 수 없습니다"만 남기면 사람이 다시 조사해야 한다.

```
자동 처리 대상에서 제외했습니다.

**사유:** 인증 로직(`middleware.ts`) 변경이 필요합니다.
TRIAGE 기준상 인증/인가 변경은 사람이 판단해야 합니다.

**참고:** 이 이슈를 자동 처리 가능하게 쪼갠다면,
인증에 영향을 주지 않는 UI 부분만 별도 이슈로 분리하면 됩니다.
```

가능하면 **쪼개는 방법을 함께 제안**한다. 그래야 다음 실행에서 처리할 수 있다.

기준이 느슨해서 이 중 하나라도 집는다면 그게 문제다.
