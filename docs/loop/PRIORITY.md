# PRIORITY — 이슈 우선순위 기준

TRIAGE를 통과해 **자동 처리 가능**으로 판정된 이슈들 중에서 하나를 고를 때 쓴다.

매 실행은 빈 컨텍스트에서 시작하므로, 모델의 그때그때 감이 아니라
**아래 순서를 기계적으로 적용**해야 실행 간 판단이 일관된다.

## 정렬 순서

앞 단계에서 동점이면 다음 단계로 넘어간다.

### 1순위 — 라벨 가중치

| 라벨 | 점수 | 이유 |
|---|---|---|
| `fix` | 100 | 깨진 것을 먼저 고친다 |
| `ci` | 80 | 파이프라인이 막히면 나머지가 전부 막힌다 |
| `docs` | 60 | 저위험·저비용 |
| `refactor` | 40 | 기능 변화 없음 |
| `chore` | 30 | |
| `feat` | 20 | 가장 위험하고 범위가 크다 |
| (라벨 없음) | 10 | |

라벨이 여러 개면 **가장 높은 점수**를 쓴다.

### 2순위 — 예상 변경 범위

작은 것부터. 큰 PR은 사람의 리뷰 부담을 키우고, 실패했을 때 되돌리기 어렵다.

| 범위 | 순서 |
|---|---|
| 단일 파일 | 먼저 |
| 단일 디렉터리 | 다음 |
| 2개 디렉터리 | 마지막 |

(3개 이상은 TRIAGE에서 이미 걸러진다.)

### 3순위 — 이슈 번호

**오래된 것부터** (번호가 작은 것부터). 방치된 이슈가 계속 밀리는 것을 막는다.

## 선택 결과 기록

고른 뒤에는 반드시 `STATE.md`에 **무엇을 왜 골랐는지** 남긴다.
후보가 여러 개였다면 탈락한 것도 한 줄씩 적는다.

이렇게 해야:
- 다음 실행이 같은 판단을 반복하지 않는다
- 사람이 "왜 저걸 골랐지?"를 나중에 확인할 수 있다
- 기준이 잘못됐을 때 어디가 잘못됐는지 추적된다

## 예시

자동 처리 가능 후보가 다음과 같다면:

| 이슈 | 라벨 | 범위 | 점수 |
|---|---|---|---|
| #150 | `feat` | 단일 파일 | 20 |
| #148 | `fix` | 2개 디렉터리 | 100 |
| #145 | `fix` | 단일 파일 | 100 |

→ **#145 선택.** `fix` 동점(#148, #145) → 범위가 작은 #145가 이긴다.
#150은 `feat`이라 점수에서 밀린다.

## 아무것도 고를 수 없을 때

자동 처리 가능한 이슈가 0개인 것은 **정상 상태**다. 실패가 아니다.

- 새 라벨을 만들거나 기준을 완화해서 억지로 하나를 집지 않는다
- `STATE.md`에 "이번 실행에서 처리 가능한 이슈 없음"과 그 근거를 남기고 종료한다
